# Feature: Agentic Workflows

**Target:** `src/workflow`
**Priority:** P1 · **Effort:** L · **Status:** Proposed (2026-11-12)
**Depends on:** 02 (AI Service v2), 06 (Reliable Jobs)

## Problem

The workflow service runs a named list of step scripts in worker threads, with schedules, history, cancel and state export. That covers deterministic pipelines. The work teams now want to automate is partly non-deterministic: triage a support email, draft a reply, call two internal APIs, ask a person to approve, then send. Building that today means writing the LLM loop, tool plumbing, retries and approval pauses by hand inside step scripts.

## Goal

A workflow can contain AI steps and human steps alongside script steps, with the framework handling the tool-use loop, retries, approvals and durable state.

## Proposal

### Step types

```javascript
await workflow.defineWorkflow('support-triage', [
  { type: 'script', script: 'load-ticket.js' },
  { type: 'ai', name: 'classify',
    model: 'claude-haiku-5-5',
    system: 'Classify the ticket. Reply with JSON.',
    schema: { type: 'object', properties: { category: { enum: ['billing', 'bug', 'other'] } } } },
  { type: 'agent', name: 'draft-reply',
    tools: ['data.find', 'search.query', 'http.get:crm'],
    maxTurns: 8, maxCost: 0.25 },
  { type: 'approval', name: 'approve-reply', role: 'support-lead', timeout: '24h' },
  { type: 'script', script: 'send-reply.js' },
]);
```

Existing string-array definitions keep working: a string is a `script` step.

- **`ai`**: one call through AI Service v2, optional schema for structured output.
- **`agent`**: a bounded tool-use loop (`maxTurns`, `maxCost`, `maxDurationMs`). Tools come from the same descriptors as the MCP server (feature 03), so one definition serves both.
- **`approval`**: the run pauses in a new `waiting` state; resume through `POST /api/runs/:id/approve` or `/reject`, the dashboard, or an emailed link.
- **`branch`**: choose the next step from the previous output (`when: 'output.category === "bug"'`, evaluated safely, no `eval`).

### Durability

Runs that wait for hours must survive a restart. Persist run state on every step boundary through the existing `workflow:state:changed` and `exportState()` hook, and add a `persistence` option that writes it with dataservice. On start, `waiting` runs resume and `running` agent steps restart from their last completed turn.

### Visibility

The execution view shows each turn of an agent step: the model's text, each tool call and result, tokens and cost. Totals roll up per run and per workflow.

## Work breakdown

1. Step-type model and validation; keep string steps as `script`.
2. `ai` and `branch` steps.
3. Shared tool registry (with feature 03); `agent` step with limits.
4. `approval` step, `waiting` state, approve/reject routes and dashboard actions.
5. Durable persistence and resume.
6. Execution view for turns, cost totals, events `workflow:step:turn`.

## Acceptance criteria

- The example above runs end to end against the `mock` AI provider in a Jest test.
- An agent step stops at `maxTurns` or `maxCost` and fails the step with a clear reason.
- A run waiting for approval survives a process restart and resumes on approve.
- No step type uses `eval` or `new Function`.

## Risks

- **Runaway cost or loops.** Hard limits per step and per workflow, with defaults.
- **Prompt injection through tool results.** Tools are scoped per step, write tools need explicit listing, and approval steps sit before irreversible actions.
