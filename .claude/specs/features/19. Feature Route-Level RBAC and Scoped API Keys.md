# Feature: Route-Level RBAC and Scoped API Keys

**Target:** `src/authservice/middleware/`, every `src/*/routes/`, `index.js`
**Priority:** P1 (security) · **Effort:** M–L · **Status:** Partly done (2026-11-13). Role grants and a route gate on `/services/*/api` (admin-tier routes explicit, the rest default by service and method); scoped API keys; production portal rule (M-1). Still open: routes are not individually declared and start-up does not fail on undeclared routes; `editor` role not created in the auth system; PATs cannot be narrowed to a subset of permissions yet.
**Fixes:** M-1, L-1 in `../go-to-market/PRODUCTION_READINESS_REVIEW_2026-11-12.md`; supports features 15 and 18

## Problem

Authorization today has two layers that don't line up:

1. **The portal guard** (`servicesAuth`) on all of `/services` requires the `admin` role, with a growing list of exemptions (filing, profile, invitations, scripts, status, static assets).
2. **The data-plane guard** (`apiKeyAuth`) accepts a static key, a personal access token or a session, **without looking at roles**.

Consequences:

- Routes documented "admin only" (users, roles, invitation approval) check only that the session is valid; they rely on the portal guard. When a path is exempted from the portal guard, as filing was, admin-level routes behind it become available to every user (C-1).
- When no admin keys are configured, every data-plane API key grants the admin portal (M-1). `app.js` configures none.
- Static API keys are all-powerful. Personal access tokens carry the owner's full role, with no narrower scope.

## Goal

Every route declares the permission it needs, and every credential carries an explicit set of permissions. Least privilege by default.

## Proposal

### Permissions

A permission is `{service}:{action}`, for example `filing:read`, `filing:write`, `filing:admin`, `jobs:run`, `workflows:define`, `users:manage`, `settings:reveal`. Roles map to permissions in one config file:

```javascript
roles: {
  admin:  ['*'],
  editor: ['filing:read', 'filing:write', 'search:query', 'knowledge:ask'],
  user:   ['filing:read', 'search:query', 'knowledge:ask', 'profile:*'],
}
```

### Enforcement

- `requirePermission('filing:write')` middleware, applied on every route (generated into the route templates by the CLI, feature 09).
- A route registry check at start-up: in `strictAuth` mode (default in production), any `/services/*/api` route without a declared permission fails start-up. A Jest test runs the same check.
- The portal guard keeps its job of protecting the dashboard pages, but is no longer the only thing between a user and an admin action.

### Credentials

- **Static API keys** get scopes: `apiKeys: [{ key, name, scopes: ['queue:*', 'data:read'] }]`. Plain string keys keep today's meaning in development, and log a warning in production.
- **Admin keys** are separate (`security.servicesAuth.apiKeys`) and required for portal access. The fallback that lets data-plane keys open the portal is removed in production mode.
- **Personal access tokens** can be created with a subset of the owner's permissions and an expiry (the `expiresInDays` option already exists).

### Authorization matrix test

A table-driven test calls every registered route as anonymous, `user`, `editor`, `admin`, a scoped key and an unscoped key, and compares the status codes with the declared permissions (feature 22).

## Acceptance criteria

- Every `/services/*/api` route declares a permission, and start-up fails in `strictAuth` mode if one doesn't.
- A `user` session gets `403` on users, roles, invitation approval, filing settings, working run, scheduling and workflow definition routes, even with the portal guard disabled.
- A data-plane key can't open `/services/` in production when admin keys aren't configured.

## Risks

- **Many routes to annotate.** Do it per service, starting with authservice, filing, working, scheduling, workflow and settings.
