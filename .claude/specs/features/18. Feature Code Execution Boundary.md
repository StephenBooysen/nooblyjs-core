# Feature: Code Execution Boundary for Working, Scheduling and Workflow

**Target:** `src/working/providers/working.js`, `src/working/routes/index.js`, `src/scheduling/routes/manager.js`, `src/workflow` (definitions and manager routes)
**Priority:** P0 (security, release blocker) · **Effort:** S–M · **Status:** Done, Phase 0 (2026-11-13)
**Fixes:** H-3 in `../go-to-market/PRODUCTION_READINESS_REVIEW_2026-11-12.md`

## Problem

Three services run JavaScript files in `worker_threads`, and all three let the caller choose the file:

- `POST /services/working/api/run` with `{ scriptPath }`.
- The scheduling manager's create-task route with `{ scriptPath, cronExpression }`.
- Workflow definitions (`defineworkflow`, manager create/import) whose steps are script paths.

`resolveActivityPath_` returns absolute paths unchanged and resolves relative paths, including `..`, without checking that the result stays inside the activities folder. Worker threads have full Node access. So any admin session, and any data-plane API key (see M-1 and feature 19), can run any `.js` file on disk. Combined with a file write (C-1, feature 15) or a stolen admin session (H-1, feature 17), that is code execution.

## Goal

Only code the operator deployed can run, and it can only be chosen by name.

## Proposal

1. **Contained resolution.** `resolveActivityPath_` uses the shared `resolveWithin()` helper (already used by filing) against the configured activities root. It rejects absolute paths and anything that escapes the root with `ClientError(400)`, and requires a `.js`/`.mjs`/`.cjs` extension.
2. **Activity registry (recommended mode).** `working({ activities: { 'resize-image': './activities/resize-image.js', … } })`. REST callers pass an activity **name**; the path never crosses the API. When a registry is configured, raw paths are refused over HTTP. In-process callers (`working.start()` in app code) may still pass paths within the root.
3. **Read-only activities root.** Document, and in Docker enforce, that the activities folder is part of the image, not a writable volume, and is outside every filing root. Fail start-up if the activities root overlaps a filing `baseDir`.
4. **Permissions.** Running, scheduling and defining workflows need the `jobs:run` / `workflows:define` permissions (feature 19), not just any API key.
5. **Audit.** Every run, schedule and definition change emits an event with the caller, activity and source (HTTP, schedule, workflow).
6. **Resource limits.** Pass `resourceLimits` (heap, stack) to workers and keep the existing timeout, so a bad activity can't exhaust the process.

## Acceptance criteria

- `POST /services/working/api/run` with `scriptPath: '/etc/passwd'` or `'../../index.js'` returns `400`; tests cover absolute, traversal, symlink-escape and wrong-extension cases.
- With an activity registry configured, only registered names run over HTTP.
- Start-up fails when the activities root is inside a filing root.

## Risks

- **Apps that pass absolute paths today.** Allow them through an explicit `allowAbsolutePaths: true` option for one minor release, with a warning.
