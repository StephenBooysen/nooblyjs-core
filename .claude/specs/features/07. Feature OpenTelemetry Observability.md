# Feature: OpenTelemetry Observability

**Target:** `index.js` (registry), `src/logging`, `src/measuring`, `src/middleware`
**Priority:** P1 · **Effort:** M · **Status:** Proposed (2026-11-12)

## Problem

NooblyJS has per-service analytics, a monitoring snapshot (`/services/api/monitoring/{metrics,snapshot}`), health probes and a structured logger. It has no distributed tracing and no standard metrics export. When a request goes HTTP → dataservice → queue → worker → AI call, there is no way to see that as one trace in Grafana, Datadog, Honeycomb or New Relic. The error handler creates a `requestId`, but it is not propagated to logs or downstream calls.

## Goal

Turn on one option and get traces, metrics and correlated logs in any OpenTelemetry backend, with zero code changes in services.

## Proposal

```javascript
serviceRegistry.initialize(app, emitter, {
  telemetry: {
    enabled: true,
    serviceName: 'orders-api',
    exporter: 'otlp',              // otlp | console | none
    endpoint: process.env.OTEL_EXPORTER_OTLP_ENDPOINT,
    sampleRatio: 0.1,
  },
});
```

The standard `OTEL_*` environment variables are honoured, so platform teams can configure it without touching code.

### What gets instrumented

- **HTTP:** a span per request with route pattern, status and user id (never the token); W3C `traceparent` accepted and returned.
- **Service calls:** the registry wraps each provider's public async methods in a span (`cache.get`, `dataservice.add`, `queue.enqueue`…), with provider and instance as attributes. Opt-out per service.
- **Queues and workers:** trace context travels inside the job envelope (feature 06), so the consumer span links to the producer.
- **AI calls:** GenAI semantic conventions: model, input/output tokens, cost, latency, tool calls.
- **Metrics:** request rate and latency histograms, queue depth and job age, cache hit rate, AI tokens and cost, worker pool usage.
- **Logs:** every logger call gets `trace_id` and `span_id`; the request id becomes the trace id.

### Dependencies

`@opentelemetry/*` packages are optional peer dependencies, loaded only when `telemetry.enabled` is true. Without them, the registry still propagates a request id through logs (async-local storage) so correlation works out of the box.

## Work breakdown

1. Request context with `AsyncLocalStorage`: request id, user, trace ids; logger includes them.
2. Optional OTel SDK bootstrap and the HTTP span middleware.
3. Registry-level method wrapping for provider calls.
4. Context propagation through queue job envelopes and worker threads.
5. GenAI spans in AI Service v2.
6. Metrics from existing analytics modules; a `docs/observability` example with a local Grafana/Tempo docker-compose.

## Acceptance criteria

- With the console exporter, one HTTP request that enqueues a job and runs it produces a single trace with linked producer/consumer spans.
- Without OTel packages installed, the app starts and logs include a request id.
- Overhead with telemetry disabled is within noise in a simple benchmark.

## Risks

- **Overhead and noise.** Sampling defaults, and a per-service opt-out.
- **Sensitive data in spans.** Never record payloads, keys or tokens by default; an allow-list for attributes.
