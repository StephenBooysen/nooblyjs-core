# Feature: Filing Authorization and Locked Settings

**Target:** `src/filing` (routes, providers), `src/authservice/middleware/services.js`
**Priority:** P0 (security, release blocker) · **Effort:** M · **Status:** Proposed (2026-11-12)
**Fixes:** C-1, L-3 in `../go-to-market/PRODUCTION_READINESS_REVIEW_2026-11-12.md`

## Problem

The filing API is exempt from the admin guard so that wiki, Teams and browser-extension users can read documents. As a result, every authenticated user can use every filing route, including:

- `POST /services/filing/api/:instanceName/settings`. It accepts `baseDir`, and path containment uses the live `this.settings.baseDir`, so any user can repoint the store at `/` and read or write any file. This was reproduced on 2026-11-12.
- Delete, git commit/push/fetch, sync push/pull/lock and auto-sync start/stop.
- Every file of every user, because there is no ownership or permission model.

## Goal

Users can do what the product needs (read, and where allowed write, documents) and nothing else. Configuration and repository operations are admin-only, and the storage root can never change at runtime.

## Proposal

### 1. Immutable root

- `baseDir` (and the S3 bucket, GCP bucket, git remote and git working directory) are construction-time options only. Remove them from `settings.list` and from `saveSettings`.
- `_resolveAndVerifyPath` resolves against a private `this.rootDir_` set once in the constructor.
- `saveSettings` accepts only an allow-list per provider (`maxFileSize`, `allowedTypes`, intervals), validates types and ranges, and rejects unknown keys with `ClientError(400)`.

### 2. Route permissions

Split the filing routes into tiers and enforce them on the route, not only through the portal guard:

| Tier | Routes | Who |
|---|---|---|
| Read | `download`, `browse`, `file-tree`, `status` | users with `filing:read` (default: any signed-in user) |
| Write | `upload`, `upload-stream`, `delete` | `filing:write` (default: `editor`, `admin`) |
| Admin | `settings` (GET and POST), `git/*`, `sync/*`, `instances`, `analytics` | `admin` |

`requireRole` / `requirePermission` comes from feature 19. Until then, add a local admin check for the admin tier.

### 3. Optional per-path access control

`acl` option: rules mapping path prefixes to roles, for example `{ 'private/': ['admin'], 'teams/finance/': ['finance'] }`, enforced on read, write and browse, and on knowledge-service retrieval (feature 05).

### 4. Safer defaults

- The library default `baseDir` becomes `./.application/files`, as `app.js` already does, never `./`.
- `allowedTypes` defaults to a safe list (see feature 17).

## Acceptance criteria

- The reproduction in `.temp/tests/review-2026-11-12/repro-invite-to-filing.js` returns `400` or `403` at the settings step and `403`/`404` for files outside the store. It is turned into a permanent Jest test in `tests/unit/security/`.
- A `user` gets `403` on every admin-tier route; an `admin` gets `200`.
- Existing filing tests pass; the dashboard still lets an admin edit `maxFileSize` and `allowedTypes`.

## Risks

- **Breaking change for apps that changed `baseDir` at runtime.** Document it; such apps should create a new instance instead.
