# Feature: Feature Flags

**Target:** `src/settings` (new `flags` module and routes)
**Priority:** P2 · **Effort:** S · **Status:** Proposed (2026-11-12)

## Problem

Trunk-based development and safe rollouts depend on feature flags. Teams using NooblyJS either add a third-party SDK or hard-code environment variables. The settings service already stores grouped, encrypted key/value settings with an embeddable UI (`SettingsUIManager`), which is most of a flag system.

## Goal

Simple, local-first feature flags with targeting and gradual rollout, managed from the existing settings UI.

## Proposal

```javascript
const flags = serviceRegistry.settings('file').flags;

if (await flags.isEnabled('new-checkout', { userId: req.user.id, roles: req.user.roles })) {
  // new path
}
const variant = await flags.variant('pricing-page', { userId });   // 'control' | 'b'
```

- Flag definition: `enabled`, `rolloutPercent` (stable hashing on a key such as `userId`), rules by role, email domain or environment, and variants with weights.
- Evaluation is in-process from a cached snapshot; changes apply within seconds through the existing settings reload and an event.
- REST: `GET/PUT /services/settings/api/flags`, `POST /api/flags/:name/evaluate` (for frontends).
- Browser helper: `flags.isEnabled()` in the settings client script, evaluated server-side for the signed-in user.
- Each evaluation can emit `flags:evaluated` for the measuring service, so rollout impact is visible.
- An OpenFeature provider adapter so teams can move to or from a hosted flag service without code changes.

## Acceptance criteria

- The same user gets the same result for a percentage rollout across restarts.
- Changing a flag in the UI changes `isEnabled` within 5 seconds, without a restart.
- Evaluation of a cached flag takes under 50 µs.

## Risks

- **Flag debt.** The dashboard shows each flag's last evaluation time and age, so stale flags are easy to remove.
