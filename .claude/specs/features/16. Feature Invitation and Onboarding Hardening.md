# Feature: Invitation and Onboarding Hardening

**Target:** `src/authservice` (routes, `authBase.js`, file provider, views)
**Priority:** P0 (security, release blocker) · **Effort:** S–M · **Status:** Done, Phase 0 (2026-11-13)
**Fixes:** C-2, part of M-3 in `../go-to-market/PRODUCTION_READINESS_REVIEW_2026-11-12.md`

## Problem

Direct registration is disabled (`/api/register` returns 403), but the invitation flow re-opens it:

- `POST /services/authservice/api/invitations` is public.
- `requestInvitation()` auto-approves the invitation.
- The response returns the invitation code to the requester.
- `POST /invitations/:code/redeem` is public and creates an active account.

So anyone can create an account in two requests, with no rate limit and no email check. This was reproduced on 2026-11-12. Invitations are also kept in a process-local Map, so they are lost on restart and not shared between replicas.

The original requirement (`.claude/steering/product/01…`) asked for "the admin user should be able to approve the invitation".

## Goal

Onboarding modes a team can choose deliberately, with the safe one as the default.

## Proposal

### Modes (`invitations.mode`)

| Mode | Behaviour |
|---|---|
| `admin-approval` (default) | A public request creates a `pending` invitation. The response never contains the code. An admin approves it, and the code is emailed to the requester (or shown to the admin to send). |
| `admin-only` | No public request endpoint. Admins create invitations (single or batch). |
| `domain-allowlist` | Public requests from allowed email domains (`invitations.allowedDomains`) are sent a code by email; other domains become `pending`. |
| `open` | Today's behaviour, for demos only. Logs a warning at start-up in production. |

### Hardening in every mode

- Rate limit public request and redeem endpoints per IP and per email (reuse the login limiter pattern; with feature 21 the counters live in Redis).
- Store only a hash of the code; compare with constant time; one-time use; expiry (already 7 days); a maximum number of failed redeem attempts per code.
- A verified email step: the code reaches the person only through the address they entered, so owning the address is proven.
- Persist invitations with the user store (file provider and others), so restarts and replicas see the same set.
- Emit `auth:invitation-requested`, `auth:invitation-approved`, `auth:invitation-redeemed` for the audit log.
- Optional CAPTCHA hook (`invitations.verifyHuman: async (req) => boolean`).

### Email delivery

Add a small mail transport to notifying (SMTP or a provider API), used for invitation codes and password resets. Without a transport, admin-approval mode shows the code to the approving admin.

## Acceptance criteria

- Steps 1–2 of the review's reproduction no longer produce a usable code in the default mode. This is covered by a permanent Jest test.
- Redeeming the same code twice fails; codes are stored hashed.
- Invitations survive a restart with the file provider.
- `open` mode logs a production warning.

## Risks

- **Existing flows that rely on auto-approval** (wiki, Teams onboarding) must choose `domain-allowlist` or `admin-approval` explicitly. Call it out in the changelog.
