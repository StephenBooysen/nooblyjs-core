# Feature: Developer CLI (`npx nooblyjs`)

**Target:** new `bin/nooblyjs.js`, `package.json` `bin`
**Priority:** P1 · **Effort:** M · **Status:** Proposed (2026-11-12)

## Problem

Starting a NooblyJS app means copying `app.js` (about 200 lines that wire every service) and trimming it. Adding a service or provider means following the conventions in CLAUDE.md and the repo skills (`new-service`, `new-provider`, `add-endpoint`) by hand. Checking that an environment is production-ready means reading `.env.example`, the Dockerfile and the go-to-market docs. The package has no `bin` entry.

## Goal

One command-line tool that creates, extends, checks and connects NooblyJS apps.

## Commands

| Command | What it does |
|---|---|
| `npx nooblyjs create my-app` | Interactive: pick services and providers, auth on/off, TypeScript or JavaScript, Docker, CI. Writes a minimal `app.js`, `.env.example`, Dockerfile, GitHub Actions workflow, and a sample test. |
| `nooblyjs add service <name>` | Scaffolds a service in an app or in core: factory, memory and API providers, analytics with `destroy()`, routes with Swagger, dashboard view, registry wiring and tests (the `new-service` skill, automated). |
| `nooblyjs add provider <service> <name>` | Adds a provider with optional-dependency handling and a contract-test entry (feature 11). |
| `nooblyjs add endpoint <service> <METHOD> <path>` | Route with both default and `:instanceName` variants, `validate()`, safe errors, Swagger entry, `.http` example, test. |
| `nooblyjs doctor` | Checks Node version, required env vars (`SESSION_SECRET`, API keys, `SETTINGS_SECRET`), `TRUST_PROXY` behind a proxy, `npm audit --omit=dev`, CSP mode, writable `.application/`, provider connectivity (Redis, Mongo, S3). Exits non-zero for CI. |
| `nooblyjs routes` | Lists every mounted route with auth requirement, from a running app or by loading it. |
| `nooblyjs mcp` | Runs the stdio MCP bridge to a running app (feature 03). |
| `nooblyjs openapi` | Writes the merged OpenAPI document and optionally a typed client (feature 10). |
| `nooblyjs keys generate` | Wraps `ServiceRegistry.generateApiKey()`. |

### Design

- Templates live in `templates/` inside the package and follow the same conventions as core (`njsc-`/`njwf-` CSS namespaces, design tokens, `ClientError`, `testDataDir()`), so generated code passes review without edits.
- No interactive prompt library dependency: use `node:readline/promises`.
- `--yes` and flags for every prompt, so agents and CI can run it non-interactively.
- The repo's `.claude/skills/` stay the source of the conventions; the CLI templates are tested to match them.

## Work breakdown

1. `bin` entry, argument parsing with `node:util.parseArgs`, `--help`.
2. `create` with three templates: API only, API + dashboards, AI app (AI Service v2 + knowledge).
3. `add service|provider|endpoint`.
4. `doctor`, `routes`, `keys`.
5. `mcp` and `openapi` once features 03 and 10 land.

## Acceptance criteria

- `npx nooblyjs create demo --yes && cd demo && npm test && npm start` works on Node 22 and 24.
- A generated service passes `tests/unit/registryListenerLeak.test.js`-style checks and the Playwright smoke test.
- `nooblyjs doctor` fails on the current advisory state and passes once it is fixed.

## Risks

- **Template rot.** CI generates each template and runs its tests.
