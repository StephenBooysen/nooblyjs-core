# Feature: Reliable Jobs

**Target:** `src/queueing` (all providers), `src/working`
**Priority:** P0 · **Effort:** M · **Status:** Partly done (2026-11-13). Engine with retries, backoff, dead letters, delays, idempotency, visibility-timeout redelivery and a consumer with graceful stop, on the memory and Redis providers (Redis verified against a real server); HTTP routes, now with Swagger entries. Still open: SQS, Azure, RabbitMQ, GCP and ActiveMQ refuse reliable options (no store); working service not migrated; no dashboard panel.

## Problem

The queue interface is `enqueue`, `dequeue`, `size`, `listQueues`, `purge`. There is no consumer API, so every app writes its own polling loop. There are no retries, no backoff, no dead-letter queue, no delayed jobs and no deduplication (only the AWS and Azure providers have a native visibility timeout). An item that fails while being processed is simply lost.

Engineers expect the BullMQ / SQS / Sidekiq model. The old usage guide even documented `queue.process()` and `queue.getJobStatus()`, which don't exist, which shows what people assume the API is.

## Goal

At-least-once job processing with retries and a dead-letter queue, on every queue provider, with one simple consumer API.

## Proposal

```javascript
const queue = serviceRegistry.queue('redis');

await queue.enqueue('emails', { to }, {
  delayMs: 60_000,                 // run no earlier than in one minute
  attempts: 5,                     // default 3
  backoff: { type: 'exponential', baseMs: 1000, maxMs: 60_000 },
  idempotencyKey: `welcome:${userId}`,   // drop duplicates within dedupeWindowMs
  priority: 'high',
});

const consumer = queue.process('emails', async (job) => {
  await sendEmail(job.data);       // throw to retry
}, { concurrency: 4, visibilityTimeoutMs: 30_000 });

await consumer.stop();             // drains in-flight jobs; wired into graceful shutdown

const job = await queue.getJob(jobId);          // { id, state, attempts, lastError, … }
await queue.retryDeadLetters('emails');
```

`enqueue` and `dequeue` keep their current signatures and behaviour; `enqueue` gains an optional third argument and returns a job id.

### Semantics

- Job states: `waiting`, `delayed`, `active`, `completed`, `failed`, `dead`.
- A job that throws is retried with backoff until `attempts` is used up, then moved to `{queue}:dead`.
- A job whose consumer dies is re-delivered after `visibilityTimeoutMs`.
- Per-provider mapping: memory (timers and maps), Redis (sorted sets for delay, lists for ready, Lua for atomic moves), SQS (native visibility, DLQ redrive), Azure Queue (native visibility), RabbitMQ (ack/nack, dead-letter exchange), GCP Pub/Sub (ack deadline, dead-letter topic). Unsupported options throw a clear error rather than being ignored.

### Working service

`working.start()` jobs get the same `attempts` and `backoff` options, and the working service runs on top of the reliable queue instead of its own loop.

### Dashboard

Per queue: counts by state, throughput, oldest waiting job age, dead-letter list with retry and delete actions.

## Acceptance criteria

- A shared contract test (feature 11) passes on memory and Redis: retry count, backoff timing, dead-letter move, delayed delivery, idempotency, redelivery after a crashed consumer.
- Existing `enqueue`/`dequeue` tests pass unchanged.
- Shutdown with in-flight jobs completes them or returns them to the queue; none are lost.

## Risks

- **Exactly-once expectations.** Document at-least-once clearly and recommend idempotent handlers (the idempotency key helps).
- **Provider parity.** Some brokers can't do everything; fail loudly on unsupported options.
