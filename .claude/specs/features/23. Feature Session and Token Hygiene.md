# Feature: Session and Token Hygiene

**Target:** `src/authservice` (middleware, routes, providers), `src/views/index.html`, `src/dataservice/views/index.html`
**Priority:** P1 (security) · **Effort:** S–M · **Status:** Partly done (2026-11-13). Query-string tokens removed; cookie hand-off endpoint, same-origin check, revocation on role/password/activation change, admin idle timeout, 90-day PATs and admin revocation are in. Still open: dashboards and login pages keep the token in `localStorage` and send it as a bearer header (about 20 files, about 90 references; the server already accepts the session cookie, so the dashboards can drop the header); PAT last-used display not verified; role change revokes sessions rather than rotating the token.
**Fixes:** M-2 in `../go-to-market/PRODUCTION_READINESS_REVIEW_2026-11-12.md`

## Problem

- Both guards accept a session token from the query string (`?authToken=`), and at least two dashboards build URLs that carry it. Tokens in URLs end up in browser history, proxy and access logs, and `Referer` headers sent to the CDNs the pages load.
- The dashboards authenticate fetch calls with a bearer session token held in page script, as well as the httpOnly session cookie. A token readable by script is exposed to any XSS (see H-1).
- Passport 0.7 regenerates the cookie session on login, but the authservice session tokens are not rotated when a user's role changes, there is no idle timeout (no `rolling` sessions), and the cookie lasts 24 hours from creation.

## Goal

Session credentials never appear in URLs or script-readable storage, and sessions follow current OWASP guidance.

## Proposal

1. **Remove query-string tokens.** Stop accepting `authToken` in the query on `/services/*` APIs. Keep it only on a one-time login hand-off endpoint that immediately exchanges it for the cookie and redirects (used by SSO and the secure-email extension flow).
2. **Cookie-only dashboards.** Dashboard fetch calls rely on the `httpOnly`, `SameSite=strict` session cookie. Bearer tokens stay for programmatic clients (personal access tokens).
3. **CSRF defence in depth.** `SameSite=strict` already blocks cross-site requests. Add a double-submit token or `Origin` check for state-changing requests, so a subdomain takeover or a lax deployment setting doesn't reopen CSRF.
4. **Rotation and timeouts.** Keep Passport's regeneration on login, and also rotate session tokens on role change. Add an idle timeout (default 30 minutes for admins) next to the absolute 24-hour lifetime. Revoke all sessions on password change.
5. **Personal access tokens.** Expiry required by default (90 days), last-used time shown in the profile page, and revocation by an admin.
6. **Referrer policy.** `Referrer-Policy: strict-origin-when-cross-origin`, or `no-referrer` on dashboards.

## Acceptance criteria

- `grep` finds no `authToken=` in dashboard markup or scripts, and API requests with `?authToken=` return `401`.
- Changing a user's role rotates their session token; changing a password invalidates existing sessions.
- An idle admin session expires after the configured timeout.

## Risks

- **Integrations that pass the token in the URL** (Teams, browser extension). Move them to the hand-off endpoint before switching off query tokens.
