# Feature: MCP Server for the Service Registry

**Target:** new `src/mcp/` (or a `mcp` option on `ServiceRegistry.initialize`)
**Priority:** P0 · **Effort:** M · **Status:** Partly done (2026-11-13). `POST /services/mcp` (off unless `mcp.enabled`) speaks JSON-RPC 2.0 over Streamable HTTP: initialize, ping, tools, resources and prompts, with batches and notifications. Read tools for logs, queues, data, search, workflows, schedules and monitoring; write tools (queue enqueue and purge, workflow run, schedule pause and resume, cache delete, settings set) only with `mcp.allowWrite` and the admin wildcard. Each tool checks the permission its REST route needs, validates input against its schema, caps result size, and emits `mcp:tool:called`. `nooblyjs mcp` is the stdio bridge. Not done: the `tests/app/mcp` demo, the dashboard card, a live Claude Code check, and the failed-run diagnosis check recorded in `.temp/tests/`.
**Depends on:** the MCP JSON-RPC core planned as phase 4 of `nooblyjs-ai-common`

## Problem

Engineers now debug and build with coding agents (Claude Code, Cursor, Copilot). Those agents speak the Model Context Protocol. A running NooblyJS app holds exactly what an agent needs to help: logs, queue depths, data containers, workflow runs, schedules, settings, search indexes. Today an agent can only reach that through ad-hoc `curl` calls to dozens of REST endpoints it has to discover first.

## Goal

Any NooblyJS app can expose its services as an MCP server, so an agent can inspect and (when allowed) operate the app in plain language: "why did last night's import workflow fail?", "how many items are stuck in the emails queue?", "add a search index for products".

## Proposal

### Transports

- **Streamable HTTP** at `/services/mcp`, behind the existing API-key and token auth (personal access tokens from authservice already work for `/services/*`).
- **stdio** through `npx nooblyjs mcp` (see feature 09), for local development against a running app.

### What is exposed

Read-only by default:

| Kind | Examples |
|---|---|
| Resources | `nooblyjs://logs/recent`, `nooblyjs://services` (registry, providers, instances), `nooblyjs://workflows/{name}`, `nooblyjs://openapi` |
| Tools (read) | `logs.search`, `queue.stats`, `data.find`, `data.count`, `search.query`, `workflow.listRuns`, `workflow.getRun`, `scheduling.listSchedules`, `monitoring.snapshot` |
| Tools (write, opt-in) | `queue.enqueue`, `queue.purge`, `workflow.run`, `scheduling.pause/resume`, `cache.delete`, `settings.set` |
| Prompts | `diagnose-failed-run`, `explain-service-config` |

Each service declares its tools in a new optional `mcp.js` next to its `routes/index.js`, so a service owns its own tool surface and the registry only aggregates.

### Safety

- `mcp: { enabled: false }` by default. Write tools need `mcp.allowWrite: true` and an `admin` role.
- Every tool input is checked against its JSON schema (common phase 5 adds the schema check).
- Every call emits `mcp:tool:called` with the user, tool and outcome, so it lands in the audit log.
- Results are size-capped (`parseLimit` / `capLimit`) and secrets are redacted (settings values are masked unless `allowReveal`).

## Work breakdown

1. Wait for, or contribute, common's JSON-RPC core and stdio server; add a Streamable HTTP server adapter there.
2. `src/mcp/index.js`: collect `mcp.js` descriptors from instantiated services; mount the HTTP transport.
3. Read tools for logging, queueing, dataservice, searching, workflow, scheduling, monitoring.
4. Write tools behind the flags above.
5. Dashboard card: connection snippet for Claude Code (`claude mcp add …`) and Cursor, plus recent tool calls.
6. Docs and a `tests/app/mcp/app-mcp.js` demo.

## Acceptance criteria

- Claude Code connects over HTTP with a personal access token and lists tools.
- With write disabled, no write tool is listed or callable.
- A failed workflow run can be diagnosed end to end by an agent using only MCP tools (manual check, recorded in `.temp/tests/`).
- Jest tests cover tool registration, auth, schema rejection and redaction.

## Risks

- **Over-exposure.** Mitigated by off-by-default, role checks, redaction and audit events.
- **Protocol churn.** Keep MCP specifics in common so the services only describe tools.
