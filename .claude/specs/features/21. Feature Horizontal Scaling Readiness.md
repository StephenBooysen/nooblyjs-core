# Feature: Horizontal Scaling Readiness

**Target:** `src/authservice` (lockout, invitations), `src/scheduling`, `src/workflow`, `src/shared/utils/`
**Priority:** P1 (production) · **Effort:** M · **Status:** Proposed (2026-11-12)
**Fixes:** M-3 in `../go-to-market/PRODUCTION_READINESS_REVIEW_2026-11-12.md`

## Problem

Sessions can already live in Redis (`SESSION_REDIS_URL`), but other state that must be shared across replicas still lives in one process:

| State | Where | Effect with N replicas |
|---|---|---|
| Login failure counters and lockout | `failedLogins` Map in `authservice/routes/index.js` | An attacker spreads attempts across replicas and gets N times the allowance |
| Invitations | in-memory Map in `authBase.js`, not persisted by the file provider | Lost on restart; a code issued by replica A is unknown to replica B |
| Cron timers | scheduling provider, workflow scheduler | Every replica fires every job, so jobs run N times |
| Workflow definitions, runs and schedules | memory provider, persisted only if the app wires `exportState()` | Each replica has its own view |
| File-backed users, data and settings | `.application/` | Writes on one replica are invisible to others, and concurrent writes can clobber each other |

## Goal

A documented, tested way to run 2+ replicas behind a load balancer, with no duplicate jobs and no security state per process.

## Proposal

1. **Shared state store.** A small `stateStore` abstraction (memory, Redis) in `src/shared/utils/`, used by the login limiter (`express-rate-limit` Redis store), the account lockout, and invitation storage.
2. **Leader election for schedulers.** A Redis lease (`SET key value NX PX ttl` plus renewal) held by one replica. Only the leader fires cron and interval tasks; on loss of the lease, another replica takes over within one TTL. Each fire also records an execution key (`schedule:{id}:{minute}`) with `NX`, so a fire can't run twice even during a hand-over.
3. **Workflow persistence by default in clustered mode.** When `cluster: { redis }` is configured, workflow state persists through dataservice (or Redis) on every change, with optimistic version checks.
4. **Clustered-mode guard.** `initialize({ cluster: { enabled: true } })` fails start-up if any configured provider is process-local (memory cache, memory queue, file dataservice, file auth), naming the provider to switch.
5. **Docs and a test harness.** A `docker-compose.cluster.yml` with two app replicas, Redis and an nginx load balancer. An integration test checks that a cron job fires once per minute and that lockout counts across replicas.

## Acceptance criteria

- With two replicas, a 1-minute cron task produces exactly one run per minute over 10 minutes.
- Five failed logins spread across two replicas lock the account.
- An invitation issued through one replica redeems through the other.

## Risks

- **Redis becomes required for clustering.** That is the common pattern; single-instance deployments are unchanged.
