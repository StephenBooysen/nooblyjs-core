# Feature: TypeScript Types and Validated Config

**Target:** package root (`types/`), every `src/{service}/index.js`
**Priority:** P0 · **Effort:** M · **Status:** Proposed (2026-11-12)

## Problem

- `package.json` has no `types` entry and the package ships no `.d.ts`. Most Node teams write TypeScript, and every editor (and every AI coding agent) relies on types for autocomplete and correctness. Today `serviceRegistry.cache('redis')` returns `any`, so `cache.set()` looks fine until it fails at runtime.
- Provider options are unchecked. A typo such as `redisUrl` (the Redis provider reads `redisurl`) or `bucket` instead of `bucketName` silently falls back to defaults.
- The code already has JSDoc on public methods, and `src/aiservice/common` already type-checks with `// @ts-check` and `npm run check:ai-common`, so most of the information exists.

## Goal

First-class types for the registry and every service, and fail-fast validation of options at startup, with no runtime cost for JavaScript users.

## Proposal

### Types

```typescript
import registry from 'nooblyjs-core';

const cache = registry.cache('redis', { redisurl: process.env.REDIS_URL });  // CacheService
await cache.put('k', { a: 1 });
const v = await cache.get<{ a: number }>('k');                                // { a: number } | undefined

const data = registry.dataService('mongodb', { connectionString, database }); // DataService
```

- Overloads per provider name, so options autocomplete per provider and a wrong provider name is a compile error.
- Generated from JSDoc with `tsc --declaration --allowJs --emitDeclarationOnly`, then hand-tuned in `types/overrides.d.ts` where JSDoc is too loose.
- `npm run check:types` in CI: type-check a set of example files in `types/tests/` (tsd-style), so the types can't drift.

### Option schemas

Each service factory gets a small `options.schema.js` (plain JSON Schema, no new dependency: a tiny validator lives in `src/shared/utils/validation.js`, which already validates routes).

- Unknown keys produce a warning listing the closest valid key ("did you mean `redisurl`?").
- Wrong types or missing required options throw at `getService()` with the service, provider and key named.
- `strictOptions: true` in `initialize()` turns warnings into errors (recommended in CI).

The same schemas feed the dashboards' settings tabs, the CLI (feature 09), the OpenAPI document (feature 10) and the MCP tool descriptions (feature 03).

### Naming fixes, without breaking callers

Add canonical camelCase aliases where option names are inconsistent (`redisUrl` alongside `redisurl`), and warn on the legacy spelling. Remove legacy spellings only in a major release.

## Work breakdown

1. Generate declarations for `index.js` and the registry factories; add `types` and `exports` to `package.json`.
2. Hand-written service interfaces for the 16 services (provider method sets verified against `providers/*.js`).
3. Option schemas for each provider, starting with the most used: logging, caching, dataservice, queueing, filing, authservice, aiservice.
4. Validator, warnings, `strictOptions`.
5. `check:types` in CI.

## Acceptance criteria

- A TypeScript project using the package compiles with `strict: true` against every example in the concise usage guide.
- `registry.cache('redis', { redisUrll: 'x' })` warns with a suggestion; with `strictOptions` it throws.
- No change in runtime behaviour for existing JavaScript callers apart from warnings.

## Risks

- **Drift between JS and types.** CI type tests and schema-driven types reduce it.
- **Warning noise in existing apps.** Warnings are logged once per key per process.
