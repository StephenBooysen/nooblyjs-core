# Feature: Knowledge Service (Retrieval-Augmented Generation)

**Target:** new `src/knowledge/` service (Level 4: logging, filing, searching, aiservice, queueing)
**Priority:** P1 · **Effort:** M · **Status:** Done for Phase 2 (2026-11-13). `registry.knowledge()` (`src/knowledge`) syncs Markdown, text, HTML and PDF files (`pdf-parse`, which is already a dependency of filing) from any filing source: heading-aware chunks and a content hash per file, so only changed files are re-embedded and deleted files lose their chunks. Unreadable files are listed as skipped with a generic reason. `watch: true` re-syncs after filing create, update and delete events. Access rules: `access(path)` returns the roles a file is open to (`*` means any signed-in caller); chunks the caller may not read are filtered out before the model sees them, and the REST routes pass the caller's roles. Sync state and feedback are saved next to the sources (`.knowledge-state.json`, `.knowledge-feedback.json`); `restore: true` re-indexes the saved chunks after a restart. `ask` answers from hybrid retrieval, cites sources by number and marks an uncited answer `low`; `askStream` and `POST /services/knowledge/api/ask/stream` stream the answer as server-sent events (`sources`, `text`, `done`). Feedback: `POST /api/feedback` records a good or bad rating, `GET /api/feedback` lists them, and good ratings can be used as evaluation cases. `evaluate()` and `POST /api/evaluate` take cases as a list or YAML and report recall@k, mean reciprocal rank and, with answers on, citation accuracy (`tests/fixtures/knowledge/eval.yaml`). The dashboard at `/services/knowledge/` has Ask (streamed, with citations and ratings), Sources and Quality tabs. Tests: Jest with a scripted stub model, and node:test with the real AI Service v2 bridge on the mock provider (`npm run test:ai-common`). Acceptance check (2026-11-13, offline, hash embeddings and the mock model): over the five top-level steering docs, "what are the dependency levels?" retrieves and cites `Application Architecture.md` > Dependency Hierarchy first. Over the whole `.claude/steering/` folder, which now also holds the feature specs, the top hit is this spec, because its acceptance criteria contain the question word for word; `Application Architecture.md` ranks fourth. Open: an evaluation with a real model and real embeddings (the harness runs on whatever the app wires).
**Depends on:** 02 (AI Service v2, `embed()`), semantic search Phase 2 (`.claude/steering/features/01…`)

## Problem

"Chat with our docs / tickets / wiki" is the most requested AI feature in internal tools. NooblyJS has every part of it in separate services: filing stores the documents (local, S3, Git, GCP), searching has BM25 and a vector engine with hybrid fusion, and aiservice calls the models. Wiring them together (chunking, embedding, keeping the index in sync with files, citing sources) is left to each team.

## Goal

One service that turns a folder or bucket into an answerable knowledge base, with citations and incremental sync.

## Proposal

```javascript
const kb = serviceRegistry.knowledge('default', {
  source: { filing: 'git', path: 'docs/' },        // any filing provider
  search: 'vector',                                 // hybrid BM25 + vectors
  ai: { provider: 'anthropic', model: 'claude-sonnet-5-5' },
});

await kb.sync();                                    // ingest new and changed files only
const answer = await kb.ask('How do I rotate the settings secret?');
// { text, citations: [{ path, title, snippet, score }], usage, cost }
kb.askStream(res, question);                        // SSE
const hits = await kb.retrieve('settings secret', { k: 8 });
```

### Pipeline

1. **Load**: Markdown (front matter via common), text, HTML, PDF (`pdf-parse`, already a dependency).
2. **Chunk**: heading-aware Markdown chunking with overlap (common phase 5 plans chunking; use it).
3. **Embed** in batches through the queue, so ingesting a large repo doesn't block requests.
4. **Index** into the searching `vector` provider, keyed by `path#chunk`, storing a content hash.
5. **Sync**: on `filing` change events (the git provider already emits fetch/commit events) re-index only changed hashes; delete removed files.
6. **Answer**: hybrid retrieve, then a grounded prompt that must cite chunk ids; strip uncited claims or flag low-confidence answers.

### REST and UI

- `POST /services/knowledge/api/ask`, `/ask/stream`, `/retrieve`, `/sync`; `GET /api/sources`, `/api/status`.
- Dashboard: sources and sync state, a chat panel with clickable citations (reuse `public/ui` chat components), and feedback buttons that record good/bad answers for evaluation.

### Evaluation

A small eval harness: a YAML file of questions and expected source paths; `kb.evaluate()` reports retrieval hit rate and answer citation accuracy. Run it in CI against the mock provider with fixed embeddings.

## Acceptance criteria

- Pointing the service at this repo's `.claude/steering/` folder answers "what are the dependency levels?" with a citation to `Application Architecture.md` (manual check).
- Changing one file re-embeds only that file's chunks.
- Works fully offline with the `hash` embedding backend and `mock` AI for tests.

## Risks

- **Index size in memory.** Respect the vector store's dimension and memory notes from the semantic search spec; offer a Postgres/pgvector provider later.
- **Access control.** Answers must not leak documents a user can't read: filter retrieval by role tags stored on chunks.
