# Feature: Safe Content Serving and a Strict CSP

**Target:** `src/filing/routes/index.js`, `src/filing/modules/uploadLimits.js`, `src/shared/utils/contentSecurityPolicy.js`, inline scripts in `src/*/views/`
**Priority:** P0 (serving) / P1 (CSP) · **Effort:** M · **Status:** Done (serving: Phase 0; strict script policy: Phase 2, 2026-11-13). Dashboards load their scripts from files, clicks use `data-onclick` handled by `/services/js/actions.js` (`nooblyArgs` builds the arguments), and the script policy has no `unsafe-inline`. The UI suite passes under enforce. Verified: `tests/ui/handlers.spec.js` opens 24 pages (the services dashboard, API docs, every service dashboard and the auth pages), collects every handler name from each page's HTML and from every script it loaded, including template strings for buttons rendered later, and checks each one resolves to a global function; it also requires every same-origin script to load as JavaScript. It found the notifying and authservice dashboards loading their page scripts from paths that returned 404 (about 20 dead buttons, such as Load settings, Assign role and Validate session); both now serve their `js/` folder. Open (Phase 3): styles still allow `unsafe-inline`, because the dashboards use many inline `style` attributes.
**Fixes:** H-1, M-4, part of L-3 in `../go-to-market/PRODUCTION_READINESS_REVIEW_2026-11-12.md`

## Problem

- Filing accepts every file type by default (`allowedTypes: '*'`).
- Downloads without `?attachment=true` are served inline with their real MIME type, including `text/html` and `image/svg+xml`, from the same origin as the `/services` admin portal.
- The CSP allows `script-src 'unsafe-inline'` and `script-src-attr 'unsafe-inline'`, because dashboards use inline scripts and `onclick` handlers.

A plain user can therefore upload an HTML or SVG file whose script runs with an admin's session when the admin opens it. The serving behaviour was reproduced on 2026-11-12.

## Goal

User-supplied content can never run script in the application origin, and the CSP stops inline script injection everywhere.

## Proposal

### Serving user content

1. **Active types are always downloads.** For `html`, `htm`, `svg`, `xml`, `xhtml`, `js`, `mjs` and unknown types, send `Content-Disposition: attachment` and `Content-Type: application/octet-stream`, whatever the query string.
2. **Sandbox header for anything inline.** Inline responses (images, PDFs, text) get `Content-Security-Policy: sandbox; default-src 'none'; img-src 'self' data:; style-src 'unsafe-inline'` and `X-Content-Type-Options: nosniff` (helmet sets the latter globally; keep it).
3. **Optional separate origin.** `filing.contentOrigin: 'https://files.example.com'` serves downloads from a different origin with short-lived signed URLs, the standard pattern for user content.
4. **Safe default type list.** `allowedTypes` defaults to documents and images (`md, txt, pdf, png, jpg, jpeg, gif, webp, csv, json, docx, xlsx, pptx`). Sniff the first bytes so a renamed HTML file is caught.
5. **Safe filenames.** Encode `Content-Disposition` filenames with RFC 5987 (`filename*=`) so quotes and CRLF can't break the header.

### Strict CSP

1. Move inline `<script>` blocks into files under each service's `views/` or `scripts/`.
2. Replace `onclick=` and other inline handlers with `addEventListener`.
3. Switch to per-request nonces for anything that must stay inline, drop `'unsafe-inline'` from `script-src`, and remove `script-src-attr 'unsafe-inline'`.
4. Keep `CSP_MODE=report-only` for one release with a report endpoint, to find stragglers, then enforce.
5. The Playwright smoke test already fails on CSP violations, so it guards the migration.

## Acceptance criteria

- Uploading `evil.html` or `evil.svg` and requesting it inline returns an attachment with `application/octet-stream`. This is a permanent test, adapted from the review reproduction.
- The production CSP has no `'unsafe-inline'` in `script-src`, and every dashboard passes the Playwright smoke test on desktop and mobile.

## Risks

- **Large mechanical change across dashboards.** Do it service by service behind `report-only`.
- **Users who previewed HTML in the browser.** Offer a sanitised preview (Markdown rendering already exists in the UI kit) instead of raw HTML.
