# Feature: Feature Flags

**Target:** `src/settings` (new `flags` module and routes)
**Priority:** P2 · **Effort:** S · **Status:** Done for the core (2026-11-16). Flag store, evaluation, targeting, rollout, variants, REST, permissions, OpenAPI, typings, browser helper and tests are in. Deferred: the dashboard panel (last evaluation time and age, stale-flag view) and the OpenFeature adapter. Measured: a cached evaluation takes about 6 µs (`isEnabled` and `variant`, Node 24-class sandbox, 200k calls); the acceptance criteria are covered by `tests/unit/settings/flags.test.js`.

## Problem

Trunk-based development and safe rollouts depend on feature flags. Teams using NooblyJS either add a third-party SDK or hard-code environment variables. The settings service already stores grouped, encrypted key/value settings with an embeddable UI (`SettingsUIManager`), which is most of a flag system.

## Goal

Simple, local-first feature flags with targeting and gradual rollout, managed from the existing settings UI.

## Proposal

```javascript
const flags = serviceRegistry.settings('file').flags;

if (await flags.isEnabled('new-checkout', { userId: req.user.id, roles: req.user.roles })) {
  // new path
}
const variant = await flags.variant('pricing-page', { userId });   // 'control' | 'b'
```

- Flag definition: `enabled`, `rolloutPercent` (stable hashing on a key such as `userId`), rules by role, email domain or environment, and variants with weights.
- Evaluation is in-process from a cached snapshot; changes apply within seconds through the existing settings reload and an event.
- REST: `GET /services/settings/api/flags`, `PUT` and `DELETE /services/settings/api/flags/:name` (the name is in the path, so a flag can be created or replaced), `POST /services/settings/api/flags/:name/evaluate` (for frontends; it uses the caller's identity and ignores the body).
- Browser helper: `flags.isEnabled()` in the settings client script, evaluated server-side for the signed-in user.
- Each evaluation can emit `flags:evaluated` for the measuring service, so rollout impact is visible.
- An OpenFeature provider adapter so teams can move to or from a hosted flag service without code changes.

## Acceptance criteria

- The same user gets the same result for a percentage rollout across restarts.
- Changing a flag in the UI changes `isEnabled` within 5 seconds, without a restart.
- Evaluation of a cached flag takes under 50 µs.

## Risks

- **Flag debt.** The dashboard shows each flag's last evaluation time and age, so stale flags are easy to remove.

## Implementation notes (2026-11-16)

- Definitions live in the settings group `flags`, so they are encrypted at rest. Each definition carries `createdAt` and `updatedAt`.
- The snapshot refreshes on `settings:updated` and `settings:created-key` in this process. Another process is picked up by a poll (`refreshMs`, default 2000 ms) that reloads only when the settings file's modification time changes. Reads never create the settings file.
- Evaluation order: unknown or disabled is off; a matching rule (role, email domain, environment) is on; otherwise the rollout hash decides. Variants use a separate hash, weighted by `weight`.
- `evaluate` emits `flags:evaluated` for each call and `flags:changed` for each write. The registry destroys the flags module on reset (`settings.analytics`).
- Permissions: management needs `settings:manage`; evaluate needs `flags:evaluate`, which the `user` and `editor` roles hold.
